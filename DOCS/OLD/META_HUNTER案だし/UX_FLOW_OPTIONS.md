# UXフロー検討: Meta Hunter Modeへの入り口

「解析ボタン」周りの挙動について、既存機能との共存を考慮した3つの案を提案します。

## 結論：【案1】ユニファイド（統合）方式を推奨

**「1回の解析で、学習モードと閲覧モードを自由に切り替えられる」** 形が最もユーザー体験が良いです。

---

## 【案1】Unified Analysis (推奨)
**「裏で全て取得し、表示を切り替える」**

1.  **ボタン**: 従来の **[ANALYZE]** ボタン1つだけ。
2.  **AIの挙動**: プロンプトを改良し、常に「解説テキスト」＋「探索用JSONデータ」の両方を出力させる。
3.  **解析完了後のUI**:
    *   画面上部に **[📝 解説モード]** と **[🎮 ハンターモード]** のタブ（またはトグルスイッチ）が出現。
    *   デフォルトは設定で記憶可能。
    *   **ハンターモード時**: 解説テキストは隠され、「画像＋未収集リスト」が表示される。
    *   **ギブアップ時**: [解説モード] に切り替えれば、すぐに答え合わせができる。

*   **メリット**:
    *   ボタンが増えず、UIがシンプル。
    *   「ゲームをしていて詰まったら解説を見る」というシームレスな学習が可能。
    *   リクエスト回数が1回で済む（経済的）。

## 【案2】Dual Buttons
**「入り口で目的を選ぶ」**

1.  **ボタン**: **[ANALYZE (Text)]** と **[PLAY HUNTER MODE]** の2つを並べる。
2.  **AIの挙動**: ボタンに応じて異なるプロンプト（テキスト用 vs ゲーム用）を送信する。
    *   Hunter Mode用プロンプトは、ネタバレ解説を出力せず、JSONデータとヒントだけを返す。
3.  **解析完了後のUI**:
    *   選んだモード専用のUIになる。

*   **メリット**:
    *   Hunter Mode時に「うっかり答えを見てしまう」事故がない。
    *   プロンプトを特化できるため、各モードの質を高めやすい。
*   **デメリット**:
    *   「やっぱり解説も読みたい」となった時、再生成（API消費）が必要になる可能性がある。

## 【案3】Lazy Loading
**「興味を持ったらゲーム開始」**

1.  **ボタン**: 従来の **[ANALYZE]** ボタンのみ。
2.  **AIの挙動**: 通常通りテキスト解説を表示。
3.  **機能**: 解説文の中に「🎮 この場所でMeta Hunterを遊ぶ」ボタンを表示。
4.  **クリック時**: 改めて画像を解析し直し（あるいは履歴から変換し）、ゲームUIを展開する。

*   **デメリット**:
    *   テンポが悪い。「最初から遊びたい」ニーズに応えられない。

---

## 技術的補足（案1の実現性）

Gemini 2.0 などの高性能モデルであれば、「詳細な解説」と「構造化データ(JSON)」を一度に出力させても十分に精度を保てます。

**プロンプト構成イメージ:**
```text
(前半: 通常の解説生成パート)
...よってここはフランスです。

(後半: システム用データ生成パート)
---
SYSTEM_DATA_START
{
  "hunter_targets": [ ... ]
}
SYSTEM_DATA_END
```
アプリ側で `SYSTEM_DATA_START` 以降を切り取って裏で処理すれば、UI上は普通の解説テキストとしても、ゲームデータとしても利用可能です。
