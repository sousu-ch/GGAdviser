# GGAdviser システム仕様書

## 1. 概要
**GGAdviser** は、GeoGuessr プレイヤーのために「AIによる地点特定支援」を提供するChrome拡張機能です。
GeoGuessrのプレイ画面から、ストリートビュー画像を自動で取得・解析し、Google Gemini を用いた推論結果をサイドパネルに表示します。

---

## 2. アーキテクチャ概要

### 2.1 全体構造
本拡張機能は、Manifest V3 に準拠した構成となっています。

- **Background Script (`background.js`):**
    - コンテキストメニューの制御、アイコンクリック時の挙動、タブ間通信のハブとして機能します。
- **Content Scripts:**
    - 各Webページ（GeoGuessr, Google Maps, Map-making.app）に注入され、DOM操作やデータ抽出を行います。
- **UI Components:**
    - 解析結果を表示するための独自のオーバーレイUI（Split View）をWebページ内に注入します。

### 2.2 データフロー
1.  **トリガー:** GeoGuessr上で `[G]キー` またはコンテキストメニュー「Analyze Here」を実行。
2.  **座標抽出:** Content Script (`geoguesser.js`) が現在のパノラマ座標を取得。
3.  **解析ページ起動:** Background経由で `map-making.app` の専用タブを開く。
4.  **キャプチャ (PanoBridge):** `map-making.app` 上で4方向（北東南西）のスクリーンショットを自動撮影。
5.  **推論実行 (Gemini):** 抽出した画像と座標情報を Gemini API に送信。
6.  **結果表示 (SplitViewManager):** 地図アプリの画面を分割し、右側にAIのアドバイスを表示。

---

## 3. 主要コンポーネント詳細

### `content_scripts/api_viewer.js`
**役割:** Map-making.app 上でのメインコーディネーター。
- `PanoBridge` と `SplitViewManager` を初期化し、Backgroundからのメッセージを受け取って各モジュールに指令を出します。
- `SHOW_RESULT`, `REMOTE_ANALYZE` などのアクションをハンドリングします。

### `content_scripts/modules/SplitViewManager.js`
**役割:** UI/UXの中核。画面分割とGeminiパネルの管理。
- **機能:**
    - マップアプリのDOM構造を変更し、右側にGemini用 `iframe` を配置。
    - 地図とパネルの境界線（Splitter）のドラッグ操作を担当。
    - **UI Toggle機能:** ヘッダーへのボタン注入と、表示/非表示の切り替え（「Floating Layout」の適用含む）。

### `content_scripts/modules/PanoBridge.js`
**役割:** ストリートビュー操作とキャプチャ。
- Google Maps API のインスタンスにアクセス（またはエミュレート）し、視点（POV）の操作や画像データの取得を行います。

### `content_scripts/utils/ToastManager.js`
**役割:** ユーザー通知。
- 画面右下に非同期のトースト通知（Success, Info, Error）を表示します。OSネイティブ通知に依存せず、ブラウザ内完結のUIを提供します。

### `content_scripts/utils/constants.js`
**役割:** 定数管理。
- セレクタ、ストレージキー、通信用メッセージIDなどを一元管理しています。

## 4. UI仕様

### Split View (Result Mode)
- **構成:** 画面を `70%（地図）` : `30%（AIパネル）` に分割。
- **Floating Layout:** 地図部分は画面端に密着させず、マージンを持たせたカード状のデザインを採用（`css/split_view.css`）。
- **レスポンシブ:** スプリッターをドラッグすることで比率を自由に変更可能。

### UI Toggle Feature
- **目的:** 解析不要時に地図アプリを広く使うため。
- **操作:** ヘッダーに追加される「GG ON/OFF」ボタン。
- **挙動:**
    - **OFF:** 拡張機能のスタイル介入を全解除。地図アプリ本来の全画面レイアウトに戻る。
    - **ON:** Floating Layout を適用し、Geminiパネルを表示。

---

## 5. 通信プロトコル
- **Extension Messaging:** `chrome.runtime.sendMessage` / `onMessage` を用いた非同期通信。
- **Iframe Messaging:** 親ウィンドウと Gemini用 `iframe` 間は `postMessage` で連携。

---

## 6. 永続化データ (`chrome.storage.local`)
- `gg_prompt_template`: ユーザー定義のプロンプトテンプレート。
- `gg_ui_enabled`: UIトグルのON/OFF状態。

## 7. 実装設計の意図 (Design Rationale)

なぜ現在の実装方式を採用したのか、その技術的背景と理由を記述します。

### 7.1 Floating Layout (フローティングレイアウト) の採用理由
- **課題:** 初期の `margin: 0` による全画面強制配置は、`map-making.app` 本来のマージンや余白設計を破壊し、OFF時にレイアウト崩れを引き起こしました。
- **解決策:** コンテンツを画面端に密着させず、`calc()` を用いて明示的にマージンを持たせた「浮き出し」配置を採用しました。
- **メリット:** 
  - ON/OFF切り替え時に、地図アプリ側のCSSと競合せず、スムーズな遷移が可能。
  - 視覚的な「めり込み」を防ぎ、各UIコンポーネントの独立性を高めることができます。

### 7.2 Button Injection Strategy (ボタン注入戦略)
- **課題:** SPA (Single Page Application) であるため、ヘッダー要素が非同期に生成・破棄されることがあり、单纯な `appendChild` ではボタンが消失したり順序が乱れたりします。
- **解決策:** ヘッダー内の永続的なランドマークである `.icon-button` を特定し、その兄弟要素として挿入する戦略をとりました。
- **メリット:** 
  - ヘッダー全体の再描画が発生しても、`.icon-button` が存在する限り、常に正しい相対位置（右隣）にボタンを復元できます。
  - 他の可変要素（右側のツールバーなど）の影響を受けずに定位置を確保可能です。

### 7.3 Scoped CSS (スコープ化されたスタイル)
- **課題:** グローバルなスタイル変更は、拡張機能が無効化された後も残留し、サイトの表示を汚染するリスクがありました。
- **解決策:** 全ての拡張機能スタイルを `body.gg-split-mode:not(.gg-ui-disabled)` というセレクタ配下に閉じ込めました。
- **メリット:** 
  - UIをOFFにした瞬間、拡張機能由来のスタイル優先度が下がり（または適用外になり）、サイト本来のCSSが「自然に」あたるようになります。これにより、JavaScriptでの複雑なスタイル復元処理を不要にしました。

### 7.4 External Capture Service (外部キャプチャサービスの利用)
- **課題:** GeoGuessr本体のゲーム画面に対して直接スクレイピングやAPIフックを行うと、アンチチートシステムに検知されるリスクが高いです。
- **解決策:** バックグラウンドで `map-making.app`（外部の地図作成ツール）を開き、そこで取得した座標を展開してキャプチャを実行するアーキテクチャを採用しました。
- **メリット:** 
  - ゲーム本体（GeoGuessr）に干渉せず、完全に分離されたコンテキストでAPI操作を行うため、**BANリスクを最小化**できます。
  - キャプチャ専用のクリーンな環境を用意できるため、UI要素の映り込みなどを防ぎ、純粋なパノラマ画像を取得しやすくなります。

### 7.5 Iframe Isolation (Iframeによる隔離)
- **課題:** コンテンツスクリプトで直接DOMにAIの回答を描画すると、ページ側のCSS影響を受けたり、逆にページのスクリプトと衝突する可能性があります。
- **解決策:** AIとの対話UIは全て `iframe` 内に閉じ込めました。
- **メリット:** 
  - **スタイルの完全分離:** ページ側のCSS（Tailwindなど）の影響を受けず、独自の美しいデザインを維持できます。
  - **セキュリティ:** サンドボックス化されるため、外部からの予期せぬスクリプト実行を防ぎます。

### 7.6 Custom Toast System (独自トースト通知)
- **課題:** `alert()` は処理をブロッキングし、ユーザー体験を損ないます。また、OSネイティブ通知はユーザー設定でオフにされていることが多いです。
- **解決策:** `ToastManager.js` を実装し、ページ内にHTMLとしてオーバーレイ表示する非同期通知システムを採用しました。
- **メリット:** 
  - **確実な伝達:** OS設定に依存せず、ブラウザを開いているユーザーに確実にメッセージを届けられます。
  - **ノンブロッキング:** ゲームプレイを中断させることなく、裏での処理完了（解析終了など）を伝えられます。

### 7.7 API Abstraction Layer (PanoBridgeによる抽象化)
- **課題:** Google Maps API の仕様変更や、対象サイトのDOM構造変更があった場合、機能全体が動かなくなるリスクがあります。
- **解決策:** ストリートビュー操作を `PanoBridge` クラスに集約し、インターフェースを統一しました。
- **メリット:** 
  - 内部実装（DOMセレクタやAPIメソッド）が変わっても、メインロジック（`api_viewer.js`）への影響を最小限に抑えられます。
  - 将来的に別の地図サービスやAPIに対応する場合も、このレイヤーを差し替えるだけで済みます。
